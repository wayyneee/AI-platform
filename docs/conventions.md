# 專案規則（conventions）

> 所有模組都要遵守的規則，**全部寫在這一份**。其他文件和 skill 不重寫這些規則，只寫「依 conventions.md」。
> 第 1～8 段是共通框架，從範本複製進來；第 9 段「本專案協定」由這個專案自己定義（write-design 負責）。
> 要改第 1～8 段，先和 PM 討論。

## 1. 每種知識的家

同一件事只寫在一個地方。

| 要知道什麼 | 放哪裡 |
|---|---|
| 怎麼安裝、啟動、測試 | `README.md` |
| 專案做什麼、為什麼、有哪些核心模組、技術選型 | `docs/design.md` |
| 所有模組都要遵守的規則 | `docs/conventions.md`（本文件） |
| 一個核心模組做什麼、小模組怎麼切、邊界、驗收條件 | `docs/modules/<Module>/spec.md` |
| 一個核心模組的畫面 | `docs/modules/<Module>/page.md`，實作前加 `page-demo/` |
| 進度、待串接、bug、想法 | `docs/progress.md` |
| 介面的精確輸入輸出 | code：`src/shared/<Module>/types` 和各層 `index` |
| 怎麼做 | code 和註解 |
| 做得對不對 | 測試（放在 code 旁邊） |
| AI 怎麼協作 | `CLAUDE.md` |

- 文件寫意圖和規則；code 寫做法。兩邊說法不同時：**意思以文件為準，精確寫法以 code 為準**。
- 只有 PM 改變決定或新增功能時才改文件。

## 2. 資料夾框架

**先分前後端，裡面再分模組。** 前端和後端是兩個不同的程式，各自是一個標準的專案；兩邊用同樣的模組名稱。每個核心模組、每個小模組都是**同一種形狀**，看懂一個，就看得懂全部。

```
<project>/
├── CLAUDE.md                    AI 協作規則
├── README.md                    安裝、啟動、測試
├── package.json 等              工具規定要放根目錄的設定檔
├── .env.example                 需要哪些環境變數（真正的 .env 不進 git）
├── docs/
│   ├── design.md
│   ├── conventions.md
│   ├── progress.md
│   ├── page-demo-kit/           demo 共用的切換列（write-page 建立）
│   └── modules/<Module>/
│       ├── spec.md
│       ├── page.md              有畫面才有
│       └── page-demo/           實作前的畫面草稿
├── src/
│   ├── shared/                  前後端都要用的：介面型別、錯誤格式定義（不放邏輯）
│   │   └── <Module>/types       各模組對外的資料型別
│   ├── server/                  後端（一個程式）
│   │   ├── main                 進入點：啟動、登記各模組，不放功能
│   │   └── <Module>/
│   │       ├── index            這個模組後端的唯一入口
│   │       └── <SubModule>/
│   │           ├── index        小模組的唯一入口
│   │           ├── <檔案>
│   │           └── <檔案>.test
│   └── client/                  前端（一個 app，例如 React）
│       ├── main                 進入點：外框、登記各模組頁面，不放功能
│       └── <Module>/
│           ├── index            這個模組前端的唯一入口
│           ├── page/            畫面元件、page.css
│           ├── texts/           這個模組的文字表
│           └── <SubModule>/     前端小模組（有才建）
├── tests/e2e/                   跨模組的端對端測試
├── public/theme/<主題>/          theme.css、art.json、<Module>/<素材>.png
└── data/                        執行時產生的資料（不進 git）
```

- spec 裡的模組、小模組名稱，和 `server/`、`client/` 底下的資料夾名稱**一模一樣**。
- 副檔名依 design.md 的技術選型。技術選型不適用這個框架（例如沒有前端）時，在 write-design 和 PM 決定怎麼調整，並改這一段。

## 3. 放置規則（新檔案放哪裡）

- **後端小模組的功能** → `src/server/<Module>/<SubModule>/`
- **某個模組的畫面** → `src/client/<Module>/page/`；**前端小模組** → `src/client/<Module>/<SubModule>/`
- **模組對外的資料型別** → `src/shared/<Module>/types`
- **很多模組都要用的機制**（log、資料路徑、主題載入、文字表、共用元件）→ 由第一個核心模組（平台基礎）提供，其他模組透過它的 `index` 使用。不另外開共用資料夾放邏輯。
- **只負責啟動、登記模組** → `src/server/main`、`src/client/main`
- **跨模組的完整流程測試** → `tests/e2e/`
- **產品附帶的圖片、主題** → `public/theme/`
- **執行時產生的資料、使用者資料** → `data/<Module>/`，資料夾不存在時由程式自動建立
- 根目錄只放 CLAUDE.md、README.md，以及工具規定要放在根目錄的設定檔。
- 找不到合適的位置時，先問 PM，不新開資料夾。

## 4. 模組邊界

- 模組和小模組**只透過 `index` 對外**。不可以引用別的模組或小模組內部的檔案，由自動檢查擋下。
- 跨核心模組時，只呼叫對方核心模組的 `index`。
- 每種資料只有一個負責的小模組，其他人透過介面取得或修改。
- 模組之間不可以互相依賴（A 用 B、B 又用 A）。出現時代表切法有問題，要和 PM 討論。
- **前端和後端互相不引用對方的檔案**，兩邊都要用的只能放在 `src/shared/`。前端不直接讀寫資料，一律透過後端的介面。

## 5. 命名

- 模組、小模組、資料型別、畫面、元件：英文 PascalCase，名稱一看就知道用途，不用縮寫，不用 Core、Manager、Utils 這類籠統的字。
- 介面、函式、變數：英文 camelCase；介面用動詞開頭，例如 `sendMessage`。
- 檔案名稱依技術選型的慣例，名稱一看就知道內容。
- 素材名稱：英文 camelCase，同一個模組內不重複。

## 6. code 與註解

目標：接手的人打開檔案，**先看註解和函式名稱就知道在做什麼**，需要時才往下看細節。

### 檔案依功能切
- 一個檔案負責**一個功能**，和這個功能相關的事都在這個檔案做完，不為了變小而拆成一堆小檔案。
- 判斷標準：看檔名就知道裡面有什麼；要改這個功能，只需要打開這一個檔案（或少數幾個）。
- 檔案長到要捲很久才找得到東西時（大約 400 行以上），再依子功能拆。

### 檔案內函式化
- 依步驟切成函式，**函式名稱說清楚它做什麼**。
- 主流程的函式讀起來像步驟清單，細節交給下面的輔助函式。
- 檔案內的順序：開頭註解 → 主要流程 → 輔助函式，用區塊註解分段。
- 函式超過一個螢幕（大約 50 行）通常代表該拆。

### 寫法簡單直接
- 依技術選型那個語言的通用風格（例如 TypeScript 的社群慣例、Python 的 PEP 8），格式交給自動格式化工具。
- 不用炫技或難懂的寫法；看起來聰明但要想很久的，換成直白的寫法。
- 巢狀不超過三層，用提早 return 或抽成函式。
- 同一段邏輯出現兩次以上，抽成函式。
- 有意義的數字和字串取名成常數，不直接寫在 code 中間。
- 變數名稱說清楚內容，不用縮寫；是/否的值用 `is`、`has` 開頭。

### 註解
- **每個檔案開頭**：一兩句說明這個檔案負責什麼。
- **區塊註解**：檔案內用註解分段，例如「讀取」「驗證」「儲存」。
- **每個對外的函式**：一句話說明用途；`index` 的介面另外說明錯誤時會回傳什麼。
- **寫「為什麼」，不寫「做什麼」**：code 已經看得出在做什麼就不重複；不直觀的寫法、特殊情況、PM 的規則，要說明原因。
- 用繁體中文。

### 範例（以 TypeScript 為例）

```ts
// 模型設定的讀取與儲存：負責模型設定檔的讀寫和格式升級。

const MODELS_FILE = 'models.json';

// ===== 讀取 =====

/** 讀取所有模型設定；檔案不存在時回傳空清單。 */
export function loadModels(): ModelConfig[] {
  const raw = readDataFile(MODELS_FILE);
  if (!raw) return [];
  return upgradeToLatest(raw).models;
}

// ===== 刪除 key =====

/** 刪除某個供應商的 key。 */
export function removeProviderKey(provider: string): void {
  const models = loadModels();
  // 只清空 key 欄位、不刪除模型：使用者換新 key 時不用重新設定模型（PM 規則）
  const updated = models.map((model) =>
    model.provider === provider ? { ...model, apiKey: '' } : model,
  );
  saveModels(updated);
}

// ===== 輔助 =====

/** 舊版格式的資料升級成目前的格式。 */

```

## 7. 測試

- 測試檔放在被測的檔案旁邊，檔名加 `.test`。跨模組的完整流程（真的開 app 操作）放在 `tests/e2e/`。
- **測試名稱用中文寫成驗收條件**，例如「刪除 key 時，只清空模型的 key 欄位」。跑完的結果就是一張看得懂的打勾清單。
- spec 的每條驗收條件，至少對應一個測試；真的沒辦法自動測的，寫成手動步驟，在 verify 時交給 PM。
- 修 bug 前，先寫一個會失敗的測試重現它，修好後留著。
- **測試不能碰正式資料**：資料路徑可以用環境變數指向暫存資料夾。
- 不跳過、不重跑、不加延遲來掩蓋不穩定的測試。找不到原因時，回報 PM。

## 8. 錯誤、log、外觀與文字

- **錯誤**：每個 `index` 的介面邊界都要接住錯誤，轉成本專案的錯誤格式（第 9 段），標明哪個模組、哪個介面。一個功能出錯，只影響那個功能，不讓整個程式當掉。
- **log**：依第 9 段的 log 原則。key、密碼、個人資料一律不寫進 log。
- **外觀**：顏色、字體、圓角、間距、陰影，只能使用主題的 CSS 變數，不寫死。
  - `public/theme/default/theme.css` 是**變數的基準表**，每個主題的變數名稱都和 default 相同，只有值不同。
  - page.css 的 class 加模組前綴（例如 ChatRoom 用 `chat-room-`），不寫全站元素的樣式。
- **素材**：用素材名稱引用，不寫死路徑。`public/theme/default/art.json` 是**素材的基準表**，每個主題的素材名稱和檔案都和 default 相同。
- **文字**：畫面上的文字一律放在 `src/client/<Module>/texts/`，不寫死在元件裡。預設語言的文字表是**文字的基準表**，其他語言的鍵必須完全相同（用型別或測試檢查）。
- 新增主題或語言時，只新增基準表的另一份，不改任何模組的 code。

## 9. 本專案協定

> 由 write-design 和 PM 討論後填寫。只寫這個專案特有、所有模組都要遵守的規則。
> 這些規則用到的機制（錯誤物件、log、資料庫工具、文字表、主題、外殼、共用元件）都由 PlatformInfrastructure 提供。

### 前後端溝通與模組登記
- HTTP + JSON，路徑為 `/api/<Module>/<介面名稱>`；串流與即時推播用 SSE。
- 錯誤回應的內容一律是 `{ error: <錯誤物件> }`。
- **後端登記**：每個核心模組的後端提供一個 Fastify plugin 登記自己的路由，後端進入點（`src/server/main`）以 `/api/<Module>` 為前綴登記。
- **前端登記**：每個有畫面的核心模組，前端提供 `getModuleRegistration`（navbar 名稱、路由路徑、放左邊或右邊、子頁面清單），由前端進入點（`src/client/main`）呼叫 PlatformInfrastructure 的 `registerModule` 登記進外殼。模組自己不呼叫 `registerModule`。
- 新增核心模組時，只需要在這兩個進入點各加一行登記。

### 錯誤格式
- 錯誤物件的欄位：模組、介面、錯誤代碼、訊息、細節（選填）。
- 錯誤代碼：大寫加底線、前面加功能名稱、全平台不重複，例如 `MODEL_KEY_INVALID`。
- 每個錯誤代碼的**等級**（警告或錯誤，見 log 原則）和**白話說明**，由定義它的模組提供；白話說明放在文字表的 `errors.<錯誤代碼>`。
- 訊息寫給開發者看：在哪一步、為什麼失敗；細節放供應商原始回應、HTTP 狀態等具體內容。
- 畫面上的錯誤訊息只顯示白話說明和來源（模組／介面／代碼），不顯示訊息和細節。
- 前端連不到後端時，一律顯示「無法連線到平台，請確認平台是否還在執行」。

### log 原則
- 所有模組都透過 PlatformInfrastructure 的 `writeLog` 寫 log。
- **一件事一筆，在事情結束時寫**：成功、失敗、被取消都算結束；排隊、等待、查進度不寫。
- **由發起這件事的地方寫**；過程中用到的底層工具（例如對供應商發請求、讀寫資料庫）不寫，只把錯誤原因完整包進錯誤物件往上丟。同一個錯誤不重複寫。
- **會改變資料、會連到外部服務**的操作：成功和失敗都寫。**單純讀取本機資料**：只在失敗時寫。
- 平台自己完成的事件（平台初始化、每一版資料庫升級）完成時寫一筆。
- **等級**：成功為「正確」；使用者造成的失敗（格式錯誤、名稱重複、找不到、自己取消）為「警告」；系統或外部造成的失敗（供應商錯誤、連不上、資料庫錯誤、逾時、未預期的錯誤）為「錯誤」。
- 後端已經記錄過、回傳給前端的錯誤，前端不再寫。
- **一律不寫進 log**：API key（只記 key 的名稱）、提示詞與對話內容、生成的內容。
- log 的文字不做多語系，直接寫繁體中文。

### 資料存放
- SQLite，使用 Node 內建的 `node:sqlite`。
- 每個核心模組的資料庫檔和媒體檔都放在自己的 `data/<Module>/`，不讀別的模組的資料。
- 一律透過 PlatformInfrastructure 的 `openDatabase` 開啟，結構用版本升級：版本從 1 開始連續遞增，**已發布的版本內容不可修改**，只能往後新增版本。
- 日期時間存 ISO 8601 文字（含時區）。
- 自動測試用環境變數 `PLATFORM_DATA_DIR` 指向暫存資料夾，不碰正式的 `data/`。

### 機密資訊
- 使用者的 API key 存在 PlatformInfrastructure 的資料庫，不加密（本機開源專案，`data/` 不進 git，由使用者自行保管）。
- 完整的 key 只有後端呼叫供應商時用到，不出現在任何回應、log、錯誤細節中；前端只顯示遮罩值。

### 畫面共通規則
- **支援的平台**：只做桌面寬度，手機寬度之後再做。
- **預設語言**：`zh-TW`（目前只有繁體中文）。文字鍵：一般文字 `<Module>.<分類>.<名稱>`，錯誤說明 `errors.<錯誤代碼>`。
- **下拉選單**：
  - 沒有預設值的選單：沒選時顯示「-- 請選擇 --」，列表最上方也有「-- 請選擇 --」可以選回未選；必填卻沒選時紅框。
  - 有預設值、一定要有值的選單（例如主題、語言）：不出現「-- 請選擇 --」。
  - 選單不會自動選第一項，預設值由各畫面決定。
- **有未儲存的修改**：目前的內容和上次儲存時（或剛打開時）不同；改回原樣就不算。
  - 有未儲存的修改時，任何離開方式都先詢問：切換頁面、瀏覽器上一頁、重新整理或關閉分頁、切換頁面內的分頁、關閉彈出視窗（X 或 Esc）。
  - 詢問一律用同一組文字：標題「尚未儲存」、說明「修改還沒儲存，確定不儲存並離開嗎？」、按鈕「不儲存並離開」。
  - 確定離開頁面後，原頁面開著的彈出視窗一併關閉。
- **儲存回饋**：按下儲存一定要有回應：儲存中按鈕轉圈、不能重複按；成功顯示綠色小字，失敗顯示紅色小字和錯誤訊息。沒有修改時儲存按鈕不能按。

### 自動檢查指令
- 尚未設定。寫第一行 code 前，用 project-init 的 B 段設定。
