# 資料夾架構規則

> 本文件是專案資料夾與檔案組織的唯一真相。架構有新規劃時，先修訂本文件，再調整實際資料夾。
> 目標：統一、乾淨的資料架構，任何東西都找得到該在哪裡。
> 本文件為**跨專案共用的通用規則**，不寫入任何單一專案的內容；專案特有的內容寫在該專案的 `docs/design.md`。

## 總覽

```
/
├── CLAUDE.md            協作規則
├── <專案設定檔>          package.json、.gitignore、.env.example 等
├── docs/                文件（唯一真相）
├── src/                 實作
├── public/              專案資源
└── data/                執行期資料（不進版本控制）
```

## 模組階層

整個專案以**兩層模組**組成：

```
專案
 ├── 大模組 A          一大塊功能（例如：系統、聊天、小說）
 │    ├── 小模組 A-1   實現大模組所需的某一項功能
 │    ├── 小模組 A-2
 │    └── …
 └── 大模組 B
      └── …
```

| 層級 | 定義 | 溝通方式 |
|---|---|---|
| 大模組 | 專案中的一大塊功能，彼此獨立 | 大模組之間只能透過大模組的對外介面溝通 |
| 小模組 | 大模組內部的功能切分，各自負責一項功能 | 同一大模組內的小模組之間，只能透過小模組的對外介面溝通 |

規則：
- 任何模組都不可直接存取其他模組的內部實作、內部狀態或資料。
- **資料採物件導向**：每一種物件（例如「角色」「知識書」）是一個資料類別，由負責它的小模組管理。
- **資料依大模組存放**：每個大模組擁有自己的資料儲存（例如一個資料庫檔），大模組內的各資料類別都放在其中；不同大模組的資料不混在一起。
- 小模組只讀寫自己負責的資料類別；需要其他小模組的資料時，透過對方的介面取得。
- 不同大模組之間的資料以 ID 關聯，需要詳細內容時透過對方大模組的介面取得；資料一致性由程式透過介面維護。
- 專案的大模組、小模組如何切分，於 `docs/design.md` 中規劃。專案規模小時，可以只有一個大模組。

## 根目錄

- 只放 `CLAUDE.md` 與**必要的專案設定檔**（工具規定要放在根目錄才讀得到的檔案，例如 `package.json`、`.gitignore`、`.env.example`）。
- 不放任何實作程式碼、文件或資源。

### 通用設定檔

以下設定檔為跨專案共用，與 `CLAUDE.md`、`structure.md` 一同複製到新專案：

| 檔案 | 用途 |
|---|---|
| `.gitattributes` | 統一換行符號為 LF（Windows 批次檔 `.bat`、`.cmd` 例外使用 CRLF），避免不同作業系統間產生無意義的差異 |

## docs/ — 文件

```
docs/
├── design.md                  設計圖：專案概觀、大模組與小模組、功能、模組如何運作與相互傳遞
├── interfaces.md              介面定義：各模組之間、前後端之間的介面串接
├── progress.md                進度表
├── structure.md               資料夾架構規則（本文件）
└── spec/
    ├── client/                前端的設計與規格（對應 src/client/）
    │   └── <大模組>/
    │       └── <頁面名>.md    單一頁面的規格：有哪些區塊、顯示什麼、使用哪些元件、串接哪些後端模組
    └── server/                後端的規格（對應 src/server/）
        └── <大模組>/
            ├── index.md       大模組概觀：職責、有哪些小模組、如何切分、資料類別
            └── <小模組>.md    單一小模組的規格：做什麼、細節怎麼做、為什麼這麼做
```

規則：
- 所有文件都放在 `docs/` 內。
- 日後新增的文件也放在 `docs/` 內。
- 同性質的文件有多份時，在 `docs/` 內建立子資料夾集中存放（例如 `spec/`）。

## src/ — 實作

### 前後端分離

網頁版與桌面版都分為前端（顯示）與後端（功能邏輯）：

```
src/
├── shared/                    共用介面與型別定義
├── client/                    前端：依大模組分組，再以頁面區分
│   ├── components/            跨大模組共用的元件
│   └── <大模組>/
│       ├── components/        本大模組內跨頁面共用的元件
│       └── <頁面名>/
│           └── <元件>         只在本頁面使用的元件
└── server/                    後端：依大模組分組，再以小模組區分
    └── <大模組>/
        ├── index              大模組對外介面
        └── <小模組>/
```

#### shared/ — 共用介面
- 存放模組之間、前後端之間共用的介面與型別定義。
- 內容依照 `docs/interfaces.md` 實作，兩者必須一致。
- 只放定義，不放任何邏輯。

#### client/ — 前端
- 前端主要負責連接後端、把內容呈現出來，不放業務邏輯。
- 先依**大模組**分組，再以**頁面**區分，最後於頁面內切分**元件**。
- 只在單一頁面使用的元件，放在該頁面資料夾內；同一大模組內跨頁面共用的元件，放在該大模組的 `components/`；跨大模組共用的元件，放在最上層的 `components/`。
- 如非必要，不切得太細。
- 每個頁面對應 `docs/spec/client/<大模組>/<頁面名>.md`。

#### server/ — 後端
- 後端負責邏輯與功能實作，依**大模組**分組，再以**小模組**區分。
- 一個大模組 = 一個資料夾，對應 `docs/spec/server/<大模組>/index.md`。
- 一個小模組 = 大模組內的一個資料夾，對應 `docs/spec/server/<大模組>/<小模組>.md`。
- 每個模組只負責自己的功能，透過介面接收與傳遞資料。
- 目的：物件導向、模組化、各自獨立。出問題時，錯誤可以鎖定在單一模組內，不會牽動整個專案。

#### 後端模組內部統一格式

```
src/server/<大模組>/
├── index                大模組對外介面：其他大模組只能透過這裡呼叫本大模組
└── <小模組>/
    ├── index            小模組對外介面：同一大模組內的其他小模組只能透過這裡呼叫
    ├── <內部實作檔案>    小模組內部邏輯，外部不可直接引用
    └── tests/           本小模組的測試檔
```

（副檔名依各專案 `docs/design.md` 的技術選型而定）

### 桌面版說明

- 桌面版同樣分為 `client/`（顯示）與 `server/`（功能邏輯）。
- 桌面版的 `server/` 指的是「後端邏輯層」，不一定是獨立運行的網路伺服器；前後端如何溝通，由各專案定義於 `docs/design.md`。
- 若某專案確實不適合分前後端，須在 `docs/design.md` 中說明理由，經 PM 確認。

## 測試

- 測試檔放在各小模組資料夾內的 `tests/`。
- PM 平時也會手動測試。

## public/ — 專案資源

- 專案需要用到的資源（圖片、字型、圖示等）都放在 `public/`。
- `public/` 只放**產品本身附帶的固定資源**（開發時放入、隨程式碼進版本控制）。使用者使用時產生的資料一律放 `data/`。

## data/ — 執行期資料

- 程式執行時產生或使用者提供的資料（資料庫檔、使用者上傳或生成的檔案、模型檔等）都放在 `data/`。
- `data/` 列入 `.gitignore`，**不進版本控制**：內容因使用者而異、可能很大、且可能含私密資料。
- `data/` 由程式在執行時自動建立，不需手動建立。
- 各大模組的資料分開存放（見「模組階層」）。
- `data/` 的子資料夾規劃、預設位置是否可更改，由各專案定義於 `docs/design.md`。
